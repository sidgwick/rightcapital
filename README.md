# 线下作业

## 项目的简单描述

此项目实现了一个通知系统, 通过对用户暴露下述能力, 抹平了不同通知系统的接入差异(但未处理不同平台入参的差异)

- 创建通知任务:
  - 可以指定以下属性
    - 信息的基本属性: 目标地址, 投递内容
    - 投递任务的属性: 投递语义, 最晚投递时间或者最多投递重试次数(超出此时间还未投成功报警), 投递失败的回调函数(或者 MQ)
  - 接口响应给调用者 `投递任务的 ID`, 此 ID 将来可用于查询/取消操作, 在成功/失败通知中, 也会传递此 ID 以标识具体是哪个投递任务
- 查询通知任务: 查询任务的投递状态
- 取消通知任务: 对没有投成功的任务, 取消投递

项目存在的问题:

1. 对新通知平台的支出需要专门再追加支持, 这个点不管什么设计, 都不能做到完全避免一个全新平台洁柔的时候 0 代码量就支持上
2. 因为缺乏具体的业务背景, 平台间的参数差异暂未处理

## 项目的设计原则

### 系统边界

- 系统只负责处理接收 + 投递 + 投递成功/失败 的处理
- 考虑到不同的下游系统可能有完全不一样的入参, 本系统不负责这些入参的组装
  - 这一条考虑将来视具体的业务情况, 如果大部分业务的参数都遵循某种模式, 可以考虑对参数再做统一的入参规定, 并在系统内部再对不同平台的入参按要求做差异化处理

### 可靠性与失败处理

- 系统对投递的结果负责, 如果投递不成功, 平台会通过回调/MQ 方式对调用方做通知
- 系统的定位是投递任务管理/执行系统, 投递语义可以由投递发起方指定, 本系统支持 `最少一次`, `至多一次`, `有且只有一次`
  - 这些语义的支持, 需要下游的接收平台对应的也实现对消息处理结果的确认, 这里默认这些系统都有类似的功能

### 取舍与演进

- 在 AI 的方案建议中，你认为哪些设计是“过度的”，并选择不采纳？
  - 我的 AI 建议加上批量通知/死信队列/限流/多线程投递等内容, 对于一个简单版本的系统我认为这些不是必要的, 因此未采纳
- 如果这是一个第一版系统，未来流量或复杂度显著增长时，你会如何演进？
  - 投递结果回调通知不再使用 HTTP 交互, 改为使用 MQ 通知(代码里不用维护 callback 调用了)
  - 流量巨大的情况下, 考虑投递任务的创建也改用 MQ 方式, 任务发送方往 MQ 发送任务请求, 投递系统消费
  - 对投递任务做优先级分类, 优先保证高优先级的任务处理(比如验证码类通知 > 营销通知)
